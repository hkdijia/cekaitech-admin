# 门店预约 admin 商业化可移植性规划

## 目标

门店预约 admin 需要同时满足两个目标：

- `cekaitech-admin` 作为自营、演示、托管和售前样板后台，能够真实管理门店预约能力。
- 门店预约 admin 不能被 `cekaitech-admin` 绑定，后续商业化时应能迁移到客户独立后台、客户私有部署后台或白标托管后台。

因此，`cekaitech-admin` 是当前首个宿主，不是唯一宿主。门店预约管理能力应沉淀为可移植的 Store Appointment Admin Pack。

## 产品分层

### 基础预约包

基础预约包是当前阶段优先收口的能力，负责跑通门店预约的管理闭环，但不处理交易和增长运营。

- 门店资料
- 项目目录
- 员工名册
- 预约规则
- 预约列表
- 预约详情
- 状态日志
- 受控状态流转
- 配置快照
- 配置回滚
- admin 配置契约

基础预约包只依赖 `miniapp-backend` 受控 API，不直连数据库，不写入客户侧私有系统。

### 商业闭环包

商业闭环包是商业化交付的必选方向，但不属于当前基础预约 admin 收口范围。支付能力最终需要实现，并应作为独立阶段设计、测试和验收。

商业闭环包至少包含：

- 支付配置
- 定金、全款、到店付策略
- 订单生成
- 微信支付或服务商模式接入
- 支付状态同步
- 退款规则
- 对账
- 到店核销
- 取消、超时和违约规则

当前阶段不得在基础预约页面中实现半成品支付入口，也不得用 `priceText` 伪装真实支付金额。后续进入商业闭环包时，必须先补齐后端契约、权限、审计、安全、退款、对账和验收设计。

### 增长运营包

增长运营包用于复购和客户经营，后续可作为可选商业模块交付。

- 会员
- 次卡
- 优惠券
- 积分
- 复购提醒
- CRM 跟进
- 客户分层
- 客户标签

增长运营包不得混入基础预约包。涉及客户画像、隐私授权、营销触达和客户账户策略时，需要独立的隐私、权限和审计设计。

## 交付形态

### CekaiAdmin 样板后台

`cekaitech-admin` 继续作为公司自营和售前展示后台，用于演示完整门店预约管理路径。

要求：

- 能展示真实门店预约管理流程。
- 能展示基础预约包的可配置能力。
- 能作为托管客户的后台入口。
- 不把内部运营术语写死到门店预约模块中。

### 白标托管后台

后续可基于同一能力包提供白标后台。

要求：

- 品牌、Logo、颜色、标题和术语可配置。
- API base URL 可配置。
- 是否启用商业闭环包、增长运营包可配置。
- 客户域名和部署环境可独立配置。

### 客户独立后台

客户若已有后台，可复用后端 API 和前端模块设计。

要求：

- 前端能力边界清晰，能按模块迁移。
- 权限码可映射到客户自身角色体系。
- 业务 API 契约稳定，不依赖 `cekaitech-admin` 的内部路由和布局。

## 可移植性约束

### 模块边界

门店预约 admin 模块应保持独立：

- API client 放在独立模块。
- 页面组件、工具函数和测试按门店预约域组织。
- 页面文案避免绑定公司内部运营口径。
- 组件不能依赖非必要的全局业务页面状态。

`cekaitech-admin` 可以提供布局、登录、路由、权限和工作区宿主能力，但门店预约业务逻辑不应反向依赖内部宿主细节。

### 品牌与术语

后续商业化交付时，下列内容需要可替换：

- 后台名称
- 品牌标识
- 主题色
- 员工称谓，例如员工、技师、顾问、老师
- 项目称谓，例如项目、服务、课程、套餐
- 门店称谓，例如门店、网点、校区、诊所

当前代码中可先使用中性文案，但新增文案不得写死为仅适合 `cekaitech-admin` 内部运营的表达。

### 租户和数据隔离

前端不能假设单租户。当前基础包至少要显式保留 `appCode` 和 `storeCode` 边界，后续商业化时应扩展或映射到租户空间。

要求：

- 数据隔离由后端鉴权和租户上下文保证，不能依赖前端筛选。
- 前端请求不得绕过 `miniapp-backend`。
- 所有写入能力都必须有权限校验和审计口径。
- 配置回滚只能作用于当前租户和门店范围。

### 权限映射

当前权限码保持模块语义：

- `admin:store-appointment:view`
- `admin:store-appointment:manage`
- `admin:store-appointment-config:manage`

商业化交付时，客户可以把这些权限映射到自己的角色体系，但模块内部不得直接绑定内部角色名。

后续商业闭环包应新增独立权限，例如：

- `admin:store-appointment-payment:view`
- `admin:store-appointment-payment:manage`
- `admin:store-appointment-refund:manage`
- `admin:store-appointment-writeoff:manage`

具体命名以后端正式契约为准。

## 支付能力路线

支付能力是商业化闭环中的关键能力，最终需要实现。但支付不应在当前基础预约 admin 收口中以半成品形式出现。

进入支付阶段前，必须先完成：

- 支付产品设计，明确定金、全款、到店付和免费预约的关系。
- 后端订单模型设计。
- 微信支付或服务商模式接入设计。
- 支付状态同步和异常补偿设计。
- 退款、取消、超时、违约规则设计。
- 对账和导出设计。
- 权限、审计、风控和操作确认设计。
- 客户交付模式设计，区分自有商户号、服务商子商户和平台代运营模式。

支付阶段不得复用 `priceText` 作为真实金额字段。真实金额、货币单位、支付渠道、支付单号、退款单号和对账状态必须来自后端正式契约。

## 迁移验收清单

基础预约包准备商业化迁移前，应至少满足：

- 门店预约页面不依赖 `cekaitech-admin` 内部业务文案。
- 基础预约 API client 只依赖 `miniapp-backend` 受控 API。
- 门店资料、项目目录、员工名册和预约规则可以按 `storeCode` 管理。
- 权限码保持模块化，不绑定内部角色。
- 配置保存请求具备 requestId 和审计基础。
- 配置回滚不会跨门店、跨租户执行。
- 页面无半成品支付、会员、核销、CRM 或客户画像入口。
- 文档明确支付是商业闭环包的未来必做能力，不属于当前基础预约包。
- 构建产物不包含客户 secret。
- API base URL、品牌和部署域名具备后续配置空间。

## 当前阶段结论

当前阶段继续在 `cekaitech-admin` 中完善基础预约包，并将其作为可演示、可托管的样板后台。

下一阶段可以继续做两类工作：

1. 基础预约包收口：提升组件边界、配置契约、验收文档和迁移清单。
2. 商业闭环包预研：先做支付产品设计和后端契约规划，不直接在当前页面落半成品支付入口。
